## What system/approach is used

This repository uses **npm** as the package manager for a single-tenant Next.js application located under `stepwise ai/app/`. Dependencies are declared in `package.json` and resolved from the public npm registry (`https://registry.npmjs.org/`) using a `package-lock.json` (lockfileVersion 3) to pin exact transitive versions. There is no monorepo workspace configuration, no vendoring of third-party packages, and no private registry or `.npmrc` present.

## Key files and packages

- `stepwise ai/app/package.json` — declares runtime dependencies (`next ^14.2.13`, `react ^18.3.1`, `react-dom ^18.3.1`) and dev dependencies (`typescript ^5.5.4`, `tailwindcss ^3.4.10`, `postcss ^8.4.38`, `autoprefixer ^10.4.19`, plus `@types/*`).
- `stepwise ai/app/package-lock.json` — lockfile generated by npm v7+ that pins every installed package and its transitive dependencies to exact versions; it also records platform-specific optional binaries (e.g. `@next/swc-*` native modules per OS/arch).
- `stepwise ai/app/node_modules/` — the local install tree produced by `npm install`; not committed via version control (see `.gitignore`).
- Build/dev scripts in `package.json` (`dev`, `build`, `start`, `lint`, `typecheck`) drive dependency usage through Next.js tooling rather than custom dependency wiring.

## Architecture and conventions

- **Single-package layout**: All source code and dependencies live in one directory (`app/`); there are no sub-packages, workspaces, or shared dependency manifests.
- **Version ranges use caret (`^`)**: Every dependency in `package.json` is pinned with a caret range (e.g. `^14.2.13`), allowing minor/patch updates while blocking major bumps. The lockfile then resolves these ranges to concrete versions at install time.
- **Lockfile-driven installs**: The presence of `package-lock.json` means reproducible builds depend on committing this file alongside `package.json`; `node_modules` itself is excluded from version control.
- **No vendoring or private registries**: No `vendor/`, `lib/` vendored copies, no `.npmrc`, no `--registry` overrides, and no `pnpm-lock.yaml` / `yarn.lock` / `bun.lockb` — the project relies entirely on the default npm registry.
- **TypeScript types as separate deps**: Type declarations are declared as explicit devDependencies (`@types/react`, `@types/react-dom`, `@types/node`) rather than bundled with their libraries, following standard TypeScript + npm conventions.

## Conventions and constraints

Observed patterns enforced by the project setup:

1. **All third-party packages must be listed in `package.json`** — runtime code imports only from `next`, `react`, and `react-dom`; build/tooling imports come from the devDependency set. No inline `require()` of arbitrary paths outside `node_modules`.
2. **Reproducible installs require the lockfile** — because `package-lock.json` is present and `node_modules` is ignored, any environment installing from this repo will resolve to the same exact versions recorded in the lockfile.
3. **Major-version boundaries are respected via `^` ranges** — the manifest deliberately allows patch/minor upgrades but blocks automatic major upgrades, keeping Next.js 14.x and React 18.x stable across environments.
4. **Platform-native binaries are handled automatically** — the lockfile includes optional `cpu`/`os`/`libc` fields for Next's SWC binaries, so installs on different platforms pull the appropriate prebuilt binary without manual configuration.

There are no documented policies, CI checks, or tooling (e.g. Dependabot, Renovate, `npm audit`) visible in the repository that enforce update cadence or security scanning; dependency maintenance is therefore manual based on the npm ecosystem.
